# Service restaurant monitoring

A warm glass dashboard based on the supplied visual reference, with four restaurants, four source-based report forms, manager routing and admin reporting windows.

## Run locally

```sh
npm install
npm run dev
```

Open http://127.0.0.1:5173 in Codex's built-in browser. `npm run build` creates `dist/`. `npm test` runs time/scoring checks and a real PostgreSQL-engine integration suite using PGlite; it does not contact Supabase.

With no `.env.local`, the app opens an explicitly labeled demo administrator workspace. Sign out to explore a fictitious restaurant manager; choosing a manager routes directly to that restaurant. Demo identities require no password and never create real users. Demo data is isolated in memory and clears on refresh. The time selector demonstrates morning, evening and late-window states.

Sample settings are **demo only**: +10 on time, −20 missed, 100 weekly baseline, Asia/Kolkata, Sunday 00:00. The demo restaurant totals include labeled fictional prior activity. Changing the demo time recalculates sample daily misses. Production has no initial policies or penalties.

The employee-management migration and authenticated Edge Function are also installed.

For a fresh replacement project, apply in this order using the Supabase SQL editor or CLI:

1. `supabase/migrations/001_restaurant_monitor.sql`
2. `supabase/seed_templates.sql`
3. `supabase/migrations/002_employee_management.sql`
4. `supabase/scheduler.sql`
5. Deploy `supabase/functions/employee-admin` as the `employee-admin` Edge Function. The dashboard editor can use `docs/employee-admin-deploy.ts`, generated by `node scripts/build-edge.mjs`. Its source contains no credentials; Supabase supplies backend secrets in the function runtime.

Set these public browser values in an ignored `.env.local` and restart Vite:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_KEY
```

Never put a database password, service-role key or Supabase management token in browser code or a `VITE_` variable. The frontend uses Supabase Auth email/password sessions and the public key under RLS.

The initial admin account was created at the owner’s request. Its login is in the ignored **ADMIN_LOGIN.local.txt** file. The one-time backend provisioning key file was removed immediately after use; no privileged key is in the browser build. No invitation emails were sent and no restaurant employees were pre-created. Sign in and open **Employees → Add employee** to create an individual manager with a name, email, initial password and restaurant. The Edge Function verifies the session and administrator role before creating an account; its server-only RPC records a manager profile and audit entry in one transaction. Client calls cannot grant administrator access. Provision additional administrators only through a trusted backend workflow. An admin has role `admin` and null restaurant; a manager has role `manager` and exactly one of `embassy-vasant`, `embassy-elan`, `kampai`, `basque`. Never permit users to self-assign their role through signup metadata. Client writes to profiles and operational tables are denied.

## Reporting rules

Admin settings create audited policy versions, effective on future business dates. Each occurrence snapshots its manager and timing/points policy. Existing occurrences retain their deadlines. Opening is the morning obligation; closing, incident declaration and briefing are the evening obligations. All four exact outlet opening/closing variants come from the supplied text appendix; the incident and briefing fields come from the four supplied Word documents.

Submission uses server time with **start inclusive / deadline exclusive**. Server RPCs lock the occurrence, check restaurant and accountable manager, validate required form data and write the immutable report plus one ledger entry in one transaction. A stale tab, client timestamp or direct API call does not bypass the cutoff. Drafts are explicitly not submissions. Issues require an action, owner and due time; they never cause additional point deductions.

`pg_cron` runs `reconcile_reports()` every minute. It creates required occurrences, recovers missing service days after downtime, skips non-operating weekdays and configured closure dates, and records one −20 entry for each overdue unsubmitted obligation. The browser does not own live penalty evaluation. Unconfigured schedules are not missed. Repeated submissions return the existing report; repeated scheduler runs cannot double-score an occurrence. Row locks serialize the submit/deadline race; the integration harness tests retries and invariants but does not simulate multiple independent database connections.

Weeks start on Sunday at the administrator's configured local reset time. The occurrence's opening instant assigns its score week, so an overnight report remains in its original week even when submitted after the reset. Weeks and ledger history are retained; no score is erased on Sunday. New weeks start from the approved baseline. An approved floor is applied only when set. Scores are attributed to the snapshotted manager. Initial baselines, awards, reset time, calendar and accountable managers must be set and approved before live activation.

Each incident remains a separate `incident_records` row; multiple incident records can be submitted together under one daily timed declaration. Activating incident scoring requires explicit approval of the daily incident/no-incident rule. Event-triggered incident deadlines are not implemented. Opening can display the previous service day's closing completer only after that linkage is approved; its original report remains linked and read only.

Manager-selected opening/closing highlights retain report/row origin, actor and time. Only authorised restaurant readers/admins see them. A separate director login and automatic negative-review classification remain unconfigured. No external channels or messages are connected.

## Before real use

Admin settings keep the unresolved business decisions visible: actual windows, +points, baseline/floor, Sunday reset, timezone, manager responsibility, calendar/closures, incident declarations, handover linkage, director access, evidence retention and staff acknowledgment. An unchecked approval blocks production activation. The database does not seed or infer these approvals.

Names entered for staff completion, attendance and incident reporter acknowledgment are attribution, **not verified signatures**. Only the logged-in manager explicitly acknowledges their own verification. Independent staff signatures and management reviewer workflows are left pending because staff identities and reviewer permissions were not supplied; the server rejects forged staff or management signature fields. Private evidence storage is provisioned with a scoped read policy, MIME/size limits and no client upload permission; uploads remain disabled pending retention and uploader policy approval.

## Validation and limits

The automated suite executes the migration, seeds, RLS policies and submission/scoring RPCs in an isolated PostgreSQL engine with mocked Supabase auth/storage schemas. Real admin authentication, installed `pg_cron`, protected tables and employee-service validation are verified in Supabase. Private evidence uploads and end-to-end concurrency between separate cloud clients still need verification before live scoring. Real admin sign-in, database scope configuration and the deployed employee service’s authenticated input validation have been checked against the owner’s project. No real manager was created just for testing. The frontend runs in the local preview; the database and employee service are live in Supabase.
